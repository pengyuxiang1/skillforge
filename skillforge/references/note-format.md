Stage 5 沉淀判断与格式规范。目标：**沉淀下来的东西，下次能直接拿来用。**

## 一、什么值得沉淀

| 值得（有其一即可） | 不值得 |
|------------------|--------|
| 出现了**新方法论**（如"hook 条件判断而非插拔"） | 常规实现（照模板填空） |
| 踩到了**新坑**（如"工具名想当然"） | 已有案例覆盖过的场景 |
| 产出可复用的**模板/脚本** | 一次性调试过程 |
| 验证方法有创新（如"造违规样本"） | 纯配置调整 |

**宁可少沉淀**。案例库的价值在于"精"，堆满了常规案例就没人看了。

## 二、双轨沉淀

| 轨道 | 位置 | 读者 | 内容 |
|------|------|------|------|
| **案例库** | `skillforge/references/cases/{skill-name}.md` | AI（下次生产时参考） | 成品规格 + 决策记录 + 增量收获 |
| **知识笔记** | 用户的外部知识库（环境无关，由用户指定去处） | 人（检索阅读） | 方法论抽象（如果够格成为独立知识点） |

**不是每个案例都要写知识笔记**——只有产生了通用方法论时才写，否则案例库够了。

## 三、案例档案格式（OKF 风格）

参考 OKF 的 `Entry + aspects` 结构：

```markdown
---
title: {skill名} 生产档案
intro: 一句话（≤30 字）说明这个 skill 做什么、沉淀了什么
keywords: [3~5 个未来会搜它的词]
date: {YYYY-MM-DD}
status: stable
verified: {YYYY-MM-DD}
stale_after: {YYYY-MM-DD}   # 涉及具体 API/版本时必须标
---
（若你的知识库有 tags / aliases / 双链等字段，按你自己的规范补充）
```

## 四、原子笔记原则

参考 Zettelkasten（卡片盒）的「临时笔记 → 永久笔记」思路：

1. **案例档案本身是原子笔记**：一个 skill 一份档案，独立可理解
2. **通用知识点要拆出去**：如果案例里出现了通用方法论（如"三个 hook 坑"），**提取成独立知识文档**，案例档案里只留链接
3. **零散发现先记，够格才提炼**：生产过程中的零散发现先写进案例档案的"增量收获"节；积累够了再提炼成独立文档
4. **不强行拆**：只有一条收获时不拆，直接留在档案里

**判断标准**：这个知识点换到别的 skill 生产时还用得上吗？
- 用得上 → 拆成独立笔记
- 只在这个案例里成立 → 留在档案

## 五、案例库索引

`references/cases/index.md` 维护索引，每条含（完整格式见 [TEMPLATE.md](cases/TEMPLATE.md)）：

```markdown
| 案例 | 工作流 | 状态数 | 引导脚本 | hook | 沉淀日期 |
|------|--------|--------|---------|------|---------|
| [{skill-name}]({skill-name}.md) | {一句话} | {N} | ✅/❌ | ✅/❌ | {YYYY-MM-DD} |
```

**新增案例必须登记**，否则下次找不到。

## 六、frontmatter 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| `title` | ✅ | 描述性标题 |
| `intro` | ✅ | ≤30 字，供索引展示 |
| `keywords` | ✅ | 3~5 个**未来会搜它的词**，与 intro 解耦 |
| `date` | ✅ | 创建日期 |
| `status` | 推荐 | stable / draft / deprecated |
| `verified` | 推荐 | 最后人工核对日期 |
| `stale_after` | 条件 | **涉及 API/版本/路径时必须填** |

> 这套字段遵循 OKF 时效规范（见 [okf-spec.md](okf-spec.md)）。时效标记的价值：未来会话检索到过期内容时能自知"该重新核对了"，而不是把两年前失效的 API 地址当成可信知识。
