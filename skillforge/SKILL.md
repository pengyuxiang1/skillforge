# skillforge

把一个工作流，从"写在 SKILL.md 里的文字协议"升级为"可执行的超级 skill"。

> **超级 skill 的定义**：有状态文件（记忆）、有引导脚本（方向）、有门禁 hook（执行）的 skill。三者缺一不可——只有状态文件是纯记录，只有引导脚本 AI 会忘记调，只有 hook 没有状态可判。
>
> 原理与论证见 [[基于openspec原理的超级skill生产方法]]。

## 怎么用（30 秒版）

```bash
# 1. 新建生产任务（生成状态文件）
python3 .codebuddy/skills/skillforge/scripts/skill_guide.py --new "<工作流名称>"

# 2. 每个动作前先跑引导 —— 它告诉你当前阶段、下一步、缺什么
python3 .codebuddy/skills/skillforge/scripts/skill_guide.py <state.md路径>

# 3. 阶段完成后推进
python3 .codebuddy/skills/skillforge/scripts/skill_guide.py <state.md路径> --advance

# 看所有进行中的生产任务
python3 .codebuddy/skills/skillforge/scripts/skill_guide.py --list
```

引导返回：`stage`（当前阶段）/ `next`（下一步）/ `how`（怎么做）/ `gaps`（缺什么）/ `checklist`（检查项）/ `reminder`（硬约束）。

**生产 skill 是长任务，可能跨会话——不要凭记忆推进，每步前跑一次引导。**

**不适用**：一次性任务、纯查询类 skill（没有流程）、纯提示词技巧（没有状态）。

## 核心：五阶段流程

```
Stage 0  接收澄清   →  问清 3 件事（触发场景 / 产物 / 判定标准）
Stage 1  复杂度评估 →  决策树判断：值不值得做？拆几个状态？知识资产怎么分（Q6）？
Stage 2  状态机设计 →  逐个推荐状态，用户确认
Stage 3  引导脚本   →  判断要不要，要就设计
Stage 4  门禁 hook  →  判断要不要，要就设计
Stage 5  验证沉淀   →  实测跑通 + 知识回填 skill + 判断是否沉淀案例
```

## Stage 0：接收与澄清

> ⚠️ **先对齐，再动手**：接收到"沉淀工作流/做个 skill"的需求时，**禁止直接开建**。先把下面四件事问清、形成工作流摘要给用户过目，用户确认"值得做、就这么做"之后才进入 Stage 1。多数口头上的"做个 skill"经 Stage 1 评估后结论是"不值得"——先讨论清楚能省掉整轮建设。

**只收事实，禁止设计**。问清五件事（缺则追问，不要猜）：

1. **触发场景**：什么情况下会用到这个工作流？（谁、什么时候、为什么）
2. **产物**：流程跑完产出什么？（文件 / 报告 / 决策 / 代码变更）
3. **判定标准**：怎么算这一步做完了？（能写成确定性检查的优先）
4. **目标 Agent**：CodeBuddy / Claude Code / Codex？（决定 hook 语法和配置文件位置，见 `references/hook-spec.md` 第零节）
5. **运行时知识沉淀位置**：skill 使用过程中持续积累的经验（新坑/新惯例/用户偏好）存哪？给用户三个选项，默认推荐 A：
   - **A. `~/.{skill-name}/`**（用户主目录，跨项目共享）——推荐默认，个人知识全项目可用，升级不丢
   - **B. Agent 工作区 `.{skill-name}/` 目录**——知识跟着项目走，团队协作可见（多人共用的 skill 选这个）
   - **C. skill 内部 `references/`**——仅当此 skill **永不分享、永不重装更新**（纯自用一次性）才可选
   - 也可由用户自定义路径。

   ⚠️ A/B 的共同目的：**skill 升级覆盖安装时，运行时知识库不被连带清除**。选 C 必须向用户明确风险后再确认。决策结果要写进新 skill 的 SKILL.md（声明沉淀路径约定），未来会话才知道往哪写、从哪读。

产出：`工作流摘要`（3~5 行），写入状态文件。

> ⚠️ 此阶段禁止写"要拆几个状态""要不要 hook"——那是 Stage 1/2 的事。

## Stage 1：复杂度评估（决策树）

**这是本 skill 的核心价值：判断，而不是套模板。**

```
Q1 这个工作流会重复执行吗？
   ├─ 否（一次性）→ ❌ 不做 skill，直接做完事就结束
   └─ 是 → Q2

Q2 步骤数量与结构？
   ├─ ≤3 步且线性 → 🟢 轻量 skill（SKILL.md + references 知识资产照做，只是不要状态机/脚本/hook）
   └─ ≥4 步，或有分支/循环 → Q3

Q3 会跨会话吗？单次执行会撑爆上下文吗？
   ├─ 否 → 🟡 单文件 skill（SKILL.md 里写清步骤 + 检查清单）
   └─ 是 → Q4（需要状态文件，进入超级 skill 范畴）

Q4 AI 容易在长任务中跑偏/忘记下一步吗？
   ├─ 是 → ✅ 加引导脚本（Stage 3）
   └─ 否 → 可选，建议加（成本低、收益稳）

Q5 有负面约束吗（不许做 X）？或有必须达成的硬标准吗？
   ├─ 没有 → ❌ 不加 hook（绝大多数 skill 到此为止）
   ├─ 有，但任务是轻量的（上下文不会撑爆）→ ❌ 仍不加。百万 token 上下文内，
   │     AI 遗忘并不明显，SKILL.md 的硬约束前置 + 引导脚本足够管住；
   │     hook 是重武器（进程开销 + 维护成本），轻任务配重武器是浪费
   └─ 有，且是超长任务/高频反复违反/改坏代价不可逆 → ⚠️ 仅此时**提名** hook，
         且必须先与用户确认性能与必要性，用户同意才建（见 Stage 4 性能预算）

Q6 知识资产怎么分？（所有 skill 必答，与 Q1-Q5 结论无关）
   领域知识按契约强度分两类，两类都不可缺：
   ├─ 契约文档（结构性规范：文件骨架/格式锚点/配色表——AI 按它生成产物，改坏 = 产物损坏）
   │     → 落 skill 的 references/，并登记校验器（修改时机器验证，不合法不让改）
   └─ 经验文档（方法论/踩坑/上游源码结论——改坏只是变差，不会"坏"）
         → 落 skill 的 references/，轻校验（frontmatter 完整即可）
         → **必须带 OKF 时效 frontmatter**（status/verified/stale_after，规范见 references/okf-spec.md）——含版本号/URL/路径/数字的内容不标 stale_after 不算完成
   注意区分两条沉淀通道：Q6 管的是「生产时知识」（建 skill 时沉淀的 references）；
   「运行时知识」（用户使用中持续积累的经验）按 Stage 0 第 5 问定的位置存——
   两者位置不同是常态：references 随 skill 分发，运行时知识独立存放防升级覆盖。
   判据（满足任一即契约文档）：① 被脚本/下游按结构消费 ② 改坏会导致产物损坏 ③ 内容是"发生了什么学到了什么"则为经验文档
   ⚠️ references/ 是必选件不是可选件——零知识沉淀的 skill，下次迭代必然从零摸索
```

**输出**：评估结论表（含每项的判断依据），推荐给用户确认后再进入 Stage 2。

判定依据参考 `references/stage-design.md`。

## Stage 2：状态机设计

**逐个推荐状态，不要一次抛给用户**。

每个状态要定义五件事：

| 字段 | 说明 | 例子 |
|------|------|------|
| `状态名` | 语义化，不是编号 | `verify`（不是 `step3`） |
| `进入条件` | 什么情况下算进入这个状态 | "已有假设清单，且有未判定的假设" |
| `产出` | 这个状态结束时必须落盘什么 | "task.md 里每条假设都有结论" |
| `判定标准` | **可机器校验**的完成条件 | "标 🟢 的假设其证据段含出处标记" |
| `下一步` | 完成后流向哪 | "全部判定 → conclude；否则留在 verify" |

**关键设计原则**：
- 状态要**有语义**（不是"文件存在"这种布尔值）
- 判定标准要**能写成代码**（否则 hook 无法校验）
- 允许**循环**（验证失败回到假设，这是长任务常态）

产出：`状态定义表` + `状态流转图`（mermaid）。

## Stage 3：引导脚本（按需）

**判断标准**：Q4 回答"是"→ 必做；否则建议做（成本低）。

脚本设计规范见 `references/guide-script-spec.md`。要点：

1. **零依赖**（Python 标准库），**只读不写**（状态文件由 AI 更新）
2. **零参数负担**：一个命令，路径可省略（自动找最新状态文件）
3. **返回结构化引导**：`stage` / `next` / `how` / `gaps` / 约束
4. **同时给"动作"和"约束"**（如 `can_write_code: false`）
5. **宽松解析**：容忍多种写法（表格/标题/列表），解析不到就提示补齐

**引导必须钉在状态文件顶部**：AI 会反复读状态文件，那是它的工作区。"记得调脚本"是会沉底的提示词，但"文件第一行写着先跑引导脚本"挂在必经之路上。

## Stage 4：门禁 hook（按需）

**判断标准**：Q5 判定"提名"（超长任务 + 硬约束 + 用户已同意）才进本阶段；否则跳过。**轻易不上 hook——hook 是最后手段，不是标配。**

### 性能预算（上 hook 前必须向用户报账）

每个 hook 触发时都要启动一个独立进程（node/python，冷启动 50-150ms），且**同一事件的多个 hook 会并行/串行叠加**。设 10 个 hook 都挂在常用事件上，Agent 每次工具调用都可能多付出几百毫秒到秒级——这是全局税，会拖慢所有会话，不只是触发门禁的场景。

上 hook 前必须和用户确认三件事：
1. **必要性**：SKILL.md 硬约束前置 + 引导脚本真的管不住吗？（多数情况管得住）
2. **性能账**：这个 hook 挂在什么事件、什么 matcher 上？非目标路径是否 10ms 内静默退出？
3. **总量账**：项目当前已挂几个 hook？再挂一个的边际成本用户接受吗？

hook 设计的性能纪律（不达标 = 不合格）：
- **静默路径必须廉价**：非目标场景（文件不匹配/无进行中任务）应在 10ms 内返回 `{}`——两层过滤的第一层（matcher）就是为省这个
- **数量克制**：项目 hook 总数控制在个位数；超过 5 个时优先考虑合并成一个 dispatcher（按路径分发），而不是继续加
- **重活异步化或前置过滤**：渲染/网络类检测（如 playwright 启动 2s+）只能挂在**低频且窄匹配**的路径上（如仅 `.excalidraw.md` 写入），绝不能挂宽 matcher

⚠️ **实现前必做两件事**：

1. **确认目标 Agent**（Stage 0 已问），并**查该 Agent 的官方 hook 文档**（优先官网，不通则读 `references/hooks-ref/` 本地快照）。三家语法不通用，字段也会废弃——照记忆写出来的配置可能被静默忽略。地址见 `references/hook-spec.md` 第零节
2. **读 `references/hook-spec.md`**，里面有三个真实踩过的坑（工具名、matcher 锚点、废弃 API），每个都会导致"门禁看起来在工作、实际从未生效"

要点：

1. **hook 常挂，脚本内判断**（不是动态插拔配置）
2. **两层过滤**：配置层 matcher 只匹配工具名；业务判断在脚本里读状态文件
3. **默认只提醒**（`systemMessage`），按需升级为阻断（`continue: false`，代价是一轮 LLM 调用）
4. **判定用 command 类型**（零 token），不用 prompt 类型（除非需要语义理解）
5. **fail-open**：脚本异常时放行，绝不因 hook 自身出错阻塞 AI

## Stage 5：验证与沉淀

### 5.1 验证（必须实测，不能"看起来对"）

| 层 | 验什么 |
|---|--------|
| L1 | 引导脚本在真实状态文件上跑通，返回的 `next` 正确 |
| L2 | 门禁脚本在"合规样本"上放行 |
| L3 | 门禁脚本在"违规样本"上拦住（**造一个违规样本**，这是最容易漏的） |
| L4 | 阶段切换后行为正确（A 阶段拦、B 阶段放行） |

### 5.2 沉淀判断

**值得沉淀**（有其一即可）：
- 出现了新的方法论（如"hook 条件判断而非插拔"）
- 踩到了新坑（如"工具名想当然"）
- 有可复用的模板/脚本

**不值得沉淀**：常规实现、已有案例覆盖过的场景。

**沉淀到哪（三个层次）**：

| 层次 | 位置 | 什么时候写 |
|------|------|-----------|
| **skill 内知识回填** | 新 skill 的 `references/`（经验文档） | **收口时必查漏**：生产过程中挖到的坑、上游源码结论、调研发现，凡 Q6 建骨架时未预见的都要回填（Q6 只在 Stage 1 建骨架，真实知识在生产中长出来） |
| 案例档案 | `references/cases/{skill-name}.md` | 值得沉淀时**必写**（给 AI 下次参考） |
| 知识笔记 | 用户的外部知识库（本 skill 环境无关，由用户指定去处） | **仅当产生通用方法论时**才写 |

> 三层各管一件事：**skill 内回填让这个 skill 更强**（用户用它时受益）；**案例档案让下次生产 skill 更强**（AI 建 skill 时参考）；**知识笔记给人检索**（跨 skill 的通用道理）。不要混——坑的细节回填 skill，只有可迁移的方法论才出外部知识库。

> ⚠️ **不是所有案例都要写进外部知识库**。多数案例留在案例库就够了——知识库是给人检索的，堆满常规案例会降低信噪比。

**格式**：见 `references/note-format.md`（OKF 风格 + 原子笔记思路）；**时效字段**（status/verified/stale_after）的完整规范见 `references/okf-spec.md`——所有沉淀文件创建时就要带，含版本/URL/路径的内容漏标 stale_after = 沉淀未完成。
**登记**：新增案例必须登记到 `references/cases/index.md`。

## 产出清单

```
{skill-name}/
├── SKILL.md                    # 主流程（必须）
├── references/                 # 知识资产（必须，Q6 两类划分）
│   ├── {契约文档}.md            #   结构规范：登记校验器，修改时门禁
│   └── {经验文档}.md            #   方法论/踩坑/调研结论：轻校验 + OKF 时效 frontmatter
├── scripts/{guide}.py          # 引导脚本（Stage 3 判定）
└── assets/{state}.md        # 状态文件模板（如需要状态文件）

（SKILL.md 正文中必须声明运行时知识沉淀路径——Stage 0 第 5 问的决策结果，
  未来会话据此知道运行时经验往哪写、从哪读）

.codebuddy/hooks/{gate}.js      # 门禁脚本（Stage 4 判定）
.codebuddy/settings.json        # hook 注册（改前先备份）

skillforge/references/cases/{skill-name}.md   # 案例沉淀（Stage 5 判定）
```

> 契约文档的校验器目前有两种形态：已有独立 hook 的（如 excalidraw-render-gate.js 直接验产物）；尚无的先在文档头部标注 `contract: true` 与校验命令，待 dispatcher hook 机制建立后统一登记。

## 设计原则

### 第一原则：让 AI 最快理解怎么用

**判断标准**：一个没见过这个 skill 的 AI，读 SKILL.md 前 20 行，能不能知道"这 skill 干什么、我该怎么开始"？

做法：
- 开头就说清"做什么 + 怎么开始"，不要先讲背景、历史、与其他 skill 的关系
- 流程用速览表（一屏看全），细节按需展开到 references
- **硬约束前置**——动手前必须知道的规范，不要放文档末尾
- 概念用表格/图，不用长段落

> 官方规范（三级加载 / 资源三分法 / 自由度分级）都是**手段**，服务于这一原则。冲突时以"AI 更快理解"为准。

### 唯一的硬机制：description 即触发（官方定，必须遵守）

AI 只读 frontmatter 的 `name` + `description` 决定是否触发。**body 只在触发后才加载**——所以"什么时候用"必须写进 `description`，写在 body 里的对触发毫无帮助。

- 硬约束：`description` ≤1024 字符、不含尖括号 `<` `>`；`name` 用 hyphen-case、≤64 字符
- frontmatter 只允许 5 个字段：`name` / `description` / `license` / `allowed-tools` / `metadata`

### Progressive Disclosure（三级加载）

| 层级 | 内容 | 加载时机 | 预算 |
|------|------|---------|------|
| 1 | `name` + `description` | 常驻 | ~100 词 |
| 2 | SKILL.md 正文 | 触发时 | <5k 词（**<500 行**） |
| 3 | references / scripts / assets | 按需 | 不限（脚本可执行不读入） |

**推论**：SKILL.md 超 500 行就拆到 references；references 只从 SKILL.md 直接链一层，不深层嵌套；超 100 行的 reference 要加目录。

### 三类资源的分工

| 目录 | 装什么 | 进上下文？ |
|------|--------|-----------|
| `scripts/` | 可执行代码（确定性、重复重写的） | ❌ 可执行不读入 |
| `references/` | 文档（按需加载的知识） | ✅ 按需 |
| `assets/` | 输出用的模板/资源（只复制/填充，不读） | ❌ |

### 不要放杂项文档

skill 里**不要**建 `README.md` / `CHANGELOG.md` / `QUICK_REFERENCE.md` 之类——只是噪音。索引类文件用 `index.md`。

### 自由度分级

按任务的脆弱程度匹配具体度：

| 自由度 | 写法 | 适用 |
|--------|------|------|
| 高 | 文字指导，留判断空间 | 多种做法都行、依赖上下文 |
| 中 | 伪代码 / 带参数的脚本 | 有偏好模式、允许变体 |
| 低 | 具体脚本、少量参数 | 脆弱易错、必须按固定顺序 |

## 与官方 skill-creator 的关系

- **本 skill 自包含**：基础规范（description 即触发 / 三级加载 / 资源三分法 / 自由度分级）已内置，校验用自带的 `scripts/validate_skill.py`（零依赖）。**只装本 skill 即可完成从创建到硬化的全流程。**
- 官方版（Anthropic `skill-creator`）**可选**：需要脚手架（`init_skill.py`）或打包分发（`package_skill.py`）时再装；它的 `quick_validate.py` 可用于交叉验证。

## 最佳实践

1. **先判断，再动手**。多数工作流不需要超级 skill——Stage 1 的结论"不做"也是有效产出。
2. **轻易不上 hook**。hook 是进程级开销 + 全局性能税，只给"超长任务 + 硬约束 + 用户确认"三者齐备的场景用；轻量 skill 靠 SKILL.md 硬约束前置就够。
3. **状态要有语义**。"文件存在"不是状态，"假设部分证实"才是。
4. **判定标准必须能机器校验**。写不出检查代码的判定标准，hook 就拦不住。
5. **吃自己的狗粮**。生产出的 skill 长什么样，先看 skillforge 自己。
6. **验证要造违规样本**。只测"能跑通"等于没测——必须证明它能拦住不该发生的。
